# Contributing to MDVault

Thanks for taking the time. MDVault is a small project with a clear scope, so
the fastest way to get a change merged is to check it fits that scope before
writing code.

## Scope

MDVault manages Markdown content **and the media it references** inside a Git
repository. Anything that keeps content plain, portable and reviewable is in
scope. Anything that introduces a database, an external asset host, or a
proprietary content format is not.

If you are unsure, open an issue first and describe the use case rather than the
solution.

## Getting set up

You need [Bun](https://bun.sh) `1.3.14` (the version CI pins), a GitHub
repository to use as content storage, and a personal access token that can write
to it — see the token permissions in the [README](./README.md).

```bash
git clone https://github.com/victor3spoir/mdvault.git
cd mdvault/mdvault
bun install

cp ../example.env .env      # then fill in GITHUB_TOKEN, GITHUB_OWNER, GITHUB_REPO
bun run dev                 # http://localhost:3000
```

> Use a **throwaway content repository** while developing. MDVault writes real
> commits, and a bug in a branch will write them for real.

## Before you open a pull request

Run what CI runs:

```bash
bun run check       # Biome — lint + format
bun run typecheck   # tsc --noEmit
bun run test        # Vitest
```

All three must pass. CI runs the same commands on every push and pull request,
plus `bun audit` and a container build.

## Branching and pull requests

- Branch from `dev`, not from `main`.
- Target `dev` in your pull request. `main` only receives releases.
- Name branches by intent: `feat/media-download`, `fix/sha-conflict`,
  `docs/token-permissions`.
- Keep one concern per pull request. A refactor and a feature in the same diff
  take three times longer to review.
- Describe **what changes for the user**, and how you verified it. Screenshots
  for anything visual.

## Commits

Short, imperative, one line of intent:

```
add download action to media library
fix sha conflict when two tabs save the same article
```

Do not commit generated output: `routeTree.gen.ts` is generated by
`bun run generate-routes`, and build artifacts stay out of the tree.

## Code conventions

The project's conventions live in [`AGENTS.md`](./AGENTS.md) — they apply to
humans and agents alike. The essentials:

- **TanStack Start** file-based routes; the page component is colocated in its
  route file.
- **TanStack Query** for data fetching, **TanStack Form** for forms — no manual
  fetch-in-effect, no hand-rolled form state.
- **Zod-validated** input on every server function; the GitHub token never
  reaches the client.
- **Biome** decides formatting and import order. Do not fight it, run it.
- New environment variables are declared and validated in the env schema, and
  documented in `example.env` and the README.

## Tests

Vitest, colocated with the code they cover. A bug fix should come with the test
that fails without it. The Git write path — commits, SHA conflict detection,
media upload — is the area where tests matter most; changes there are held to a
higher bar than UI work.

## Reporting bugs

Include: MDVault version (or image tag), how you run it (container or source),
whether the content repository is public or private, the action you took, and
what you expected. If a commit was involved, its message helps — MDVault writes
descriptive ones on purpose.

**Never paste a GitHub token, even a revoked one, into an issue.**

## Security issues

Do not open a public issue. See [SECURITY.md](./SECURITY.md).
